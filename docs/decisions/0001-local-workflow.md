# 0001：先实现单机人工审核闭环

- 日期：2026-10-09
- 状态：历史决策，适用 0.1–0.2 本地版本；主流程与目录导入边界由 [0006：来源无关的截图识别服务](0006-recognition-service.md) 替代
- 范围：获授权截图导入 → 模型候选 → 人工确认 → SQLite 订单与事件 → XLSX 快照

0.3.0 起，图片接收 → 模型提取 → 未经人工核实的结构化结果成为主流程；人工审核、订单与 XLSX 仅为可选下游，目录扫描停止。本文保留历史依据，其中精确金额、证据隔离、人工确认后方可成为正式订单、事务/幂等、备份与安全约束继续适用。

## 背景与目标

首次实现需要可运行、可复现、可故障恢复的最小闭环，同时遵守既有代码规范：数据库是事实源；模型不能确认订单；重复和重试不能重复记账；秘密与客户数据不得进入公开仓库。

尚未确定微信官方接入、多用户协作、在线表格目的地及真实模型供应商的商业与数据处理条件，因此这些能力不作为已完成事项。默认演示完全离线、不产生模型费用，真实客户上线仍需明确授权、字段、商品目录和保留策略。

## 决策

### 1. 运行与界面

使用 Python 3.12 作为开发/CI 基线，uv 管理依赖并提交真实生成的 `uv.lock`。FastAPI 提供本地 API 和原生 JavaScript 审核界面；不引入独立前端构建链、消息队列或云服务。

默认监听回环地址 `127.0.0.1:8000`。初始化在受控数据目录创建 SQLite schema 与随机访问令牌。业务 API 通过 Bearer token 鉴权；模型凭据只由后端读取。界面中的操作者字段用于记录操作上下文，不是经身份服务验证的独立用户。

一个数据目录仅由一个服务进程持有文件锁。SQLite 使用外键、事务、唯一约束及版本检查。本版本不支持多 worker、多主机、网络共享数据库文件或安全的公网服务。数据根目录默认在仓库外的 `~/.ocrs`。

### 2. 输入及识别边界

提供图片上传与可选的受控收件目录导入，每张图片独立建任务，当前不跨图合并；同图内可有多笔订单。操作者先手动保存有权处理的微信截图，系统不抓取聊天、不注入客户端、不绕过微信访问控制。

保存文件摘要、来源标签和受控图片引用。摘要与来源标签共同进行技术去重；同一图片在另一个业务场景中可使用不同标签。技术重复与业务重复分开处理，疑似业务重复仅警告，不自动合单。

默认 `demo` 适配器产生醒目标记的虚构候选，**完全不执行 OCR**。`openai-compatible` 适配器由后端发起显式允许的请求，要求模型名、服务地址、密钥与外传开关。启用开关本身不能取代处理真实客户数据所需的授权。截图中的文字和模型响应均为不可信数据，不授予工具或执行权限。

所有响应通过版本化 schema 和本地字段校验后仍是候选。未知字段、缺失值、异常数量、未知商品及证据关联必须在边界处理；不自动补成“1 件”或“0 元”。供应商返回的证据只是待核对声称，不是事实认证。

### 3. 人工确认与数据事实

原始证据、历次候选、正式订单、订单明细和事件分别存储。候选可包含新单、改单与撤单动作，必须经过人工确认。改单以完整明细集合为新版本，已有明细可通过稳定 `line_id` 保持身份；撤单保留明确状态与历史。

确认必须提供有效任务版本；改单/撤单还需目标订单、预期订单版本和原因。并发页面遇到旧版本必须失败并重新核对，不能静默覆盖。幂等请求键与有效载荷绑定，同键异内容拒绝。

订单、明细、业务事件与 outbox 在同一事务中提交。识别外部网络调用和导出文件写入不放在订单事务中。可失败的导出不能撤销已确认订单。

金额与数量使用 `Decimal`，数据库保存十进制字符串。当前币种精度支持 CNY/USD/EUR/GBP 两位与 JPY 零位，明细以 `ROUND_HALF_UP` 舍入，再精确求和。不推断税、运费、折扣或截图里未定义的总额口径。

### 4. 导出选择

每次生成独立 XLSX 快照，从数据库的已确认订单重建，不从旧 Excel 反推事实，也不打开旧文件覆盖手填列。导出保留内部订单/明细标识、版本与状态，以支持核对。撤单保留状态，不能看见一行就当作仍有效订单。

文件先写入临时位置并验证，再以同文件系统的硬链接原子发布不可变快照；不覆盖既有文件，文件系统需支持硬链接。导出任务与 outbox 状态可核对和重试；导出失败时正式订单保持不变。所有客户/模型可控内容按显式文本单元格写入，防公式注入。可信数字列遵守 Excel 的表示能力，精确业务事实仍以数据库为准。

这避免了首次实现中共享文件锁、人工列合并和在线表格重试带来的复杂性。在线表格 upsert 与用户手填列同步是后续独立设计，当前不实现。

### 5. 隐私、备份与保留

测试、示例、CI 和仓库只能使用虚构数据。图片、数据库、导出和备份均保存在受控的本机位置；没有应用级静态加密或多租户隔离，应依赖操作系统权限、磁盘加密和受控备份介质。

备份与恢复在服务停止后执行，备份使用 SQLite backup API 而不是仅复制正在写入的数据库文件。恢复只允许新数据目录，避免覆盖现有业务；恢复后需要检查证据引用、订单版本、事件、outbox 及重新生成的导出。

原图默认保留窗口 30 天，通过明确的运维命令清理，同时清除对应候选和候选历史，不后台自动删除。过期后保留可核对的状态，不能再声称可回放原图。事件、订单、导出和旧备份需要各自的保留方案；当前版本没有自动归档/到期删除。这些资料可能仍包含个人信息，清理图片不等于完成全部数据删除。

## 替代方案与取舍

- PostgreSQL、分布式队列、多用户身份服务：适合后续协作与规模化，当前增加部署和恢复成本。需要多人共享或更多吞吐量时重新评估。
- 自动采集微信：没有明确且获授权的受支持接入方案，当前仅保留人工截图入口。
- 按置信度自动确认：与人工确认约束冲突，未实施。
- 持续改写同一 Excel：容易覆盖手填列并扩大对账范围，改用每次独立快照。
- 把 demo 包装成真实 OCR：会误导准确率与上线判断，明确使用虚构数据模式。

## 验证与后续条件

运行命令见 [README](../../README.md)，维护流程见 [OPERATIONS](../OPERATIONS.md)。单元/集成测试应覆盖候选隔离、精确金额、版本冲突、幂等、改单撤单、失败重试、公式安全和备份恢复。CI 仅运行离线检查及构建，不部署、不上传客户数据、不调用付费模型。

真实模型效果、不同 Excel 客户端打开效果、真实业务字段与授权、操作系统差异、备份介质和保留期限仍需在上线环境验证。没有执行的检查必须写为“未运行”，不能由设计或测试文件的存在推断已经通过。
