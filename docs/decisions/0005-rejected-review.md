# 0005：驳回记录修订与重新审核

- 日期：2026-10-10
- 状态：采用，适用 0.2.5
- 范围：保存候选修正、驳回后提交复审、审核队列当前页选择与逐条编辑

## 行为与边界

已驳回记录可再次进入人工审核。保存修正与提交复审是两个明确动作：保存只更新当前候选并保留原状态；提交复审只把已驳回记录恢复为 `review_required`。两者均不调用识别服务，不增加识别次数，不创建正式订单或导出事件。正式订单仍须另行人工确认。

保存修正允许未完成的候选，字段类型、长度与证据来源仍按候选契约校验；完整必填、商品目录、金额和目标订单版本继续在正式确认时检查。不确定字段可保留 null，不自动补值。

审核队列的勾选范围限当前页。全选只包含本页可编辑记录，选中多条后按顺序逐条进入详情编辑；不把同一组字段批量覆盖到不同记录。切换搜索、筛选、分页或显式刷新清空选择，重新加载页面也不恢复旧选择。每条保存或提交均使用自己的版本与审计原因。

## 证据、历史与并发

原模型 `candidate_history` 不修改；人工修订保存到独立 `candidate_revisions`，包含任务版本、候选快照、操作者、原因和时间。驳回、修订及恢复审核的审计按时间展示，包含状态变更及版本；旧审计没有版本信息时显示为旧记录，不编造版本。

保存与提交复审都要求 `expected_version` 和幂等键。事务内检查状态、版本、证据有效性，再原子写入候选/审计/幂等回执。相同键与内容重放返回原回执，同键异内容拒绝；并发旧版本不覆盖新结果。取消编辑只丢弃浏览器草稿，不发送保存。未知请求结果保留同一幂等键供核对和重试。

`PUT /api/tasks/{id}/candidate` 接受 `expected_version`、`idempotency_key`、`actor`、`reason` 和完整 `candidate`；`POST /api/tasks/{id}/reopen` 接受相同元数据但不接受候选字段。两者返回轻量 `{id, status, version}` 回执，避免在幂等缓存保留候选副本；调用方再读取详情。详情增加 `model_candidate`、`candidate_revisions` 和 `review_history`，分页列表不附加完整历史。原有接口继续可用，鉴权和跨站防护仍适用。

没有候选或证据已过期的记录不能通过此接口恢复审核，界面说明限制；本次复审功能不会代替识别或自动外传证据。

## 数据兼容与恢复

业务 schema 从 2 追加迁移至 3：新增人工候选修订表，审计增加可空的任务版本及前后状态字段；schema 1 依次经 2 升级。已有订单、模型候选、驳回理由及外传授权保留。升级前停止服务并运行既有备份流程，再安装锁定依赖及运行 `ocrs init`。旧程序拒绝 schema 3；回退应使用升级前备份恢复到新目录，不能把旧程序指向已升级数据库。

业务备份包含新增修订和审计，恢复保留版本及历史；模型配置和密钥仍不进入业务备份。显式证据清理一并删除对应人工候选快照，审计保留既有策略。迁移和验证只在隔离测试数据上运行，不修改用户正在运行的服务。
